# PROJECT_CONTEXT.md

## 1. Назначение проекта
Проект **anime_channel** — это автоматизированная система для периодической публикации аниме в Telegram‑канал.

Основные цели:
- хранить локальную базу аниме (SQLite);
- выбирать аниме для публикации по заданным правилам (cooldown, статус, приоритет);
- публиковать посты в Telegram;
- предотвращать слишком частые повторы, но допускать повторную публикацию спустя время.

Проект рассчитан на долгоживущую эксплуатацию и постепенное расширение логики.

## 5. Ключевая логика

### scripts/get_random_anime.py

Ответственность:
- выбрать аниме, **которое можно публиковать сейчас**
- учитывать:
  - отсутствие публикаций
  - cooldown по статусу
  - повторную публикацию спустя время
  - самокоррекцию приоритетов (перекос жанр/год/статус в последних N публикациях)

Использует:
- `can_publish(anime, last_pub)` — источник истины по правилам допуска (cooldown не меняется)
- `app.priority_weights`: статистика последних N публикаций, множители штрафов, итоговый вес = базовый вес × штраф

### app/priority_weights.py

Ответственность:
- собирать статистику по последним N публикациям (жанр, год выпуска, статус);
- считать множители (< 1) для перепредставленных категорий;
- выдавать итоговый множитель для конкретного аниме (произведение по статусу, году, жанрам).

Не меняет cooldown и can_publish; только влияет на порядок перебора кандидатов через эффективный вес.


### scripts/post_random_anime.py

Ответственность:
- получить аниме через `get_random_anime`
- отправить пост в Telegram
- записать публикацию в `published_anime`

После этапа сервисного слоя: `scripts/post_random_anime.py` — тонкий entry point, вызывает `services.post_cycle.run_post_cycle()`.


### bot/formatter.py

Ответственность:
- преобразовать объект Anime в текст поста;
- при отсутствии описания в БД или после очистки — выводить заглушку «Описание отсутствует.».


### bot/telegram_sender.py

Ответственность:
- отправка сообщений через Telegram API

## 6. Текущие правила публикации (ЭТАП D — зафиксировано)

- Аниме **может публиковаться повторно**
- Cooldown зависит от статуса:
  - released → 90 дней
  - ongoing → 14 дней
  - anons → 30 дней
- Рейтинг **не является ключевым фактором**
- Старые аниме продолжают попадать в выборку
- Ongoing **не публикуются по каждой серии**, только по времени

---

## 6.1. Система самокоррекции приоритетов (ЭТАП E)

**Цель:** при перекосе выборки (один жанр, один год, один статус доминируют в последних постах) временно снижать приоритет этих категорий.

**Где хранятся веса:**
- Базовые веса (год, статус) — в коде `get_random_anime.calculate_weight`.
- Штрафы **не хранятся**: вычисляются при каждом выборе из последних N записей `published_anime`.

**Статистика последних N публикаций:**
- Запрос: последние N строк `published_anime` по `published_at DESC`, с загрузкой Anime и жанров.
- Считаются счётчики: по статусу, по годовой корзине (old, 2000–2009, 2010–2014, 2015–2019, 2020+), по жанру (genre_id).

**Как меняются веса:**
- Для каждой оси (статус, год, жанр): ожидаемое число = N / число категорий в окне; для категории с числом actual множитель = min(1, expected/actual), снизу ограничен MIN_PENALTY (0.3).
- Для аниме: итоговый множитель = произведение множителей по его статусу, годовой корзине и всем его жанрам. Эффективный вес = базовый вес × этот множитель.

**Возврат к норме и ограничение перекоса:**
- Возврат к норме автоматический: окно скользящее, старые посты выходят — штрафы ослабевают.
- Нижняя граница множителя MIN_PENALTY не даёт категории полностью исчезнуть из выборки.

**Коэффициенты (app/priority_weights.py):** WINDOW_SIZE = 30, MIN_PENALTY = 0.3, YEAR_BUCKETS — константы, расширяемо.

## 6.2. Надёжность и устойчивость (ЭТАП F)

**Цель:** бот должен работать неделями без присмотра, не падая из‑за единичной ошибки и оставляя понятные логи.

### Логирование и формат

- Централизованная настройка логирования: `app/logging_config.py`, стандартный модуль `logging`.
- Скрипты при старте вызывают `setup_logging()`, что настраивает:
  - единый формат: `%(asctime)s [%(levelname)s] %(name)s: %(message)s`;
  - вывод в консоль (stderr) и в лог‑файл (путь и уровень могут задаваться через переменные окружения, см. будущие этапы).
- Логируются:
  - старт процессов (публикация, загрузка аниме, smoke‑тесты);
  - попытки и результаты публикаций;
  - отказы и критические ошибки с полным traceback.

### Изоляция ошибок

- `scripts/get_random_anime.py`:
  - при любом исключении (ошибка БД, ошибка в системе самокоррекции и т.п.) — логирование `logger.exception("Ошибка при выборе аниме")` и возврат `None`;
  - отсутствие кандидатов логируется как debug, бизнес‑логика не меняется.
- `scripts/post_random_anime.py`:
  - внутри `post_random_anime()` при ошибке публикации — rollback сессии, `logger.exception("Ошибка публикации")`, функция возвращает управление вызывающему коду;
  - в блоке `if __name__ == "__main__"` окружено глобальным `try/except`: любые неожиданные ошибки логируются с traceback и приводят к контролируемому завершению процесса.
- `bot/telegram_sender.py` и `scripts/load_anime.py`:
  - ключевые действия (отправка в Telegram, загрузка аниме) и все исключения логируются через стандартный `logging`, одиночные ошибки не «ломают» остальные элементы цикла.

### Dry‑run режим (план)

- Будет добавлен флаг dry‑run (через настройки или переменную окружения), который:
  - проходит всю логику выбора аниме и форматирования поста;
  - **не** отправляет сообщение в Telegram;
  - **не** создаёт запись в `published_anime`;
  - явно логирует `DRY RUN: сообщение НЕ отправлено и НЕ записано`.

### Smoke‑тест живости (план)

- Отдельный скрипт `scripts/smoke_test.py` будет:
  - проверять подключение к БД (простой запрос через `SessionLocal`);
  - проверять валидность токена Telegram (например, через `Bot.get_me()` без отправки сообщений);
  - возвращать однозначный статус `OK` / `ERROR` (по exit‑коду и в логах).

## 8. Известные ограничения / временные решения

- SQLite редактируется только через скрипты
- Нет миграций БД
- Нет тестов

**Загрузка `.env` и `RuntimeState`:** значения `POST_INTERVAL_MIN` / `POST_INTERVAL_MAX`, `POSTING_ENABLED`, `DRY_RUN` читаются при создании `STATE` в `app/runtime_state.py`. Файл `.env` подгружается через `load_dotenv()` в начале `runtime_state.py` и до импорта `STATE` в `app/settings.py`, чтобы интервалы и флаги совпадали с `.env` при старте процесса.

**Сетевые ошибки Telegram:** при недоступности API (`NetworkError`, в т.ч. `getaddrinfo failed` на Windows) библиотека повторяет long polling. В `bot/telegram_bot.py` такие случаи пишутся одной строкой уровня WARNING без полного traceback; прочие ошибки по-прежнему логируются с traceback.
